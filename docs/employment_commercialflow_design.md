# 商流位置・雇用形態の抽出設計書

**作成日**: 2026-07-25
**背景**: 「所属：1社先正社員」が単に「正社員」と判定され、商流情報（1社先）が失われていた実害を起点に設計。
関連コード: `supabase/functions/inbound-email/index.ts` の `extractEmploymentType` / `parseEmploymentValue` / `normalizeShaNum`。

## 0. なぜ2次元に分けるのか

営業上の判断は「**この人を、うちの会社からの紹介で客先常駐させられるか**」。この問いに一発で答えるには、以下の2つを分けて持つ必要がある:

- **商流位置**: 紹介ルートの近さ。自社の人なら直接動かせる／N社先ならN社挟む（マージン薄・多重派遣リスク）
- **雇用形態**: その人の縛り。正社員は要調整／フリーは動きやすい 等

「1社先正社員」のように両者が1語に複合した表記も、分けて保持する。

## 1. 出力する2フィールド（raw_profile）

| キー | 値 | 意味 |
|---|---|---|
| `commercialFlow` | `自社` / `1社先` / `2社先` / `3社先`… / `null` | 商流位置。自社=直接可・N社先=N社挟む・null=不明 |
| `employmentType` | `正社員` / `フリーランス` / `契約社員` / `派遣社員` / `業務委託` / `null` | 純粋な雇用形態。SESは正社員に開く（§3） |

## 2. 何が来たら何になるか（判定表）

| 入力（所属/立場/雇用形態ラベルの値・または文脈） | commercialFlow | employmentType |
|---|---|---|
| 正社員 / 弊社正社員 / (正社員) / 正社員エンジニア | 自社 | 正社員 |
| フリーランス / フリー / 個人事業主 | 自社 | フリーランス |
| 契約社員 | 自社 | 契約社員 |
| 派遣社員 / 派遣 | 自社 | 派遣社員 |
| 業務委託 | 自社 | 業務委託 |
| SES / 弊社SES / SESエンジニア | 自社 | 正社員（§3・案B） |
| 1社先 / 一社先 / １社先 | 1社先 | null（形態不明） |
| 1社先社員 / 一社先社員 | 1社先 | 正社員 |

## 3. 考え方（設計判断）

### 3.1 商流を雇用形態より優先して評価する
旧ロジックの実害は「ラベル値の中で `正社員` チェックが `N社先` チェックより先に走り、`1社先正社員` が `正社員` に潰れた」こと。
→ **N社先（商流）を先に判定し、雇用形態と独立に両方を保持する**。`parseEmploymentValue` は1つの値文字列から商流・形態を並行抽出する。

### 3.2 表記ゆれの正規化
- 漢数字（一二三…）→ アラビア数字（1,2,3…）: `normalizeShaNum`
- 全角数字（０１２…）→ 半角
- → 「1社先」「一社先」「１社先」は全て `1社先` に統一する（分裂させない）

### 3.3 SESは「該当商流の正社員」に開く（案B）
用途（客先常駐できるか）では「SESです」という語自体が答えになっていない。SESの実態は「どこかの会社の正社員が客先常駐する働き方」なので:
- 弊社SES → `自社` ＋ `正社員`
- N社先SES → `N社先` ＋ `正社員`
に分解する。「客先常駐に慣れている」というプラス情報は、そもそも常駐前提で探しているため暗黙に効いており、SESという語を残す必要は薄い。

### 3.4 商流はあるが雇用形態が不明なケース（1社先単独）
「1社先」だけで形態の記載がない場合、`employmentType=null` のままにする。商流バッジ `[1社先]` だけでも「パートナー経由で紹介可能」という肝心の情報は出るため、無理に正社員等と推測して誤りを混ぜない（欠損の方が安全という既存方針を踏襲）。

### 3.5 「自社」の付与ルール
商流の記載（N社先）がなく、雇用形態だけが取れた場合は `commercialFlow='自社'` とみなす。「弊社正社員」等は自社の人という前提。

## 4. UI表示（人材カード・2バッジ）

- **商流バッジ**（色分け）: 自社=緑 / 1社先=黄 / 2社先=赤 …（深いほど警戒色）
- **雇用形態バッジ**（グレー）: 正社員 / フリーランス / 契約社員 / 派遣社員 / 業務委託
- 一目で「紹介の近さ（商流）＋その人の縛り（形態）」が分かる。

## 5. 既存データ移行（2026-07-25実施済み）

prod約3,795件に対して以下を実施:
1. 既存 `employmentType` 値を上表に従い (商流, 形態) に分解し `commercialFlow` を追加、`employmentType` を純粋な形態に正規化
2. 「所属：N社先正社員」がラベル経路で `正社員` に潰れていた54件を、生テキストの所属ラベル値から商流を再判定して補正
3. 表記ゆれ（一/1/１社先）を `1社先` に統一

移行後分布: 自社 2,061 / 1社先 310 / 2社先 1（+ 商流なし＝形態自体がnullの人）。

## 6b. 勤務条件（常駐可否）— 生フレーズ主役＋ざっくりタグ（2026-07-25）

商流・雇用形態と違い、リモート/常駐/出社の条件は**自由記述が非常に多く、拠点別・条件付きのニュアンス**を持つ（例:「フルリモート（梅田／神戸は常駐可能）、東京は初日・緊急時出社可」）。これを3〜4カテゴリに分類すると「関西なら常駐に出せる」等の営業上の最重要情報が潰れる。

**設計判断（ユーザー合意）**: 分類だけに頼らず、**メール本文の記載文をそのまま保存して人が判断**する。加えてシステムのざっくりタグを併記する。

- `workStyleNote`（主役）: 本文からリモート/常駐/出社/在宅を含む文を抜き出した生フレーズ（`extractWorkStyleNote`）
- `workStyleTag`（ヒント）: `常駐可` / `併用可`（ハイブリッド=一部出社可） / `リモート希望`（常駐は難しい） / null。`deriveWorkStyleTag`で導出
- UI表示: 「**タグ（本文: 生フレーズ）**」。タグがズレても本文で人が正せる

**タグ判定の考え方（precedence）**:
1. フルリモートのみ/必須/常駐不可 かつ 出社OKシグナルなし → `リモート希望`
2. リモート語 と 出社/常駐語 の両方あり（=ハイブリッド）→ `併用可`（一部常駐可能）
3. 柔らかいフルリモート/リモート優先/頻度高め（出社言及なし）→ `リモート希望`
4. 出社/常駐語のみ → `常駐可`
5. リモート語のみ → `併用可`

**重要な実データ知見**: 旧ロジックは「フルリモート」「週N日出社可」等の特定タグ表現しか拾えず、prod 3,440件のnullのうち**2,110件（61%）が本文にリモート/常駐/出社の記載を持つのに取りこぼしていた**。生フレーズ抽出でこの2,110件を回収（移行後: 常駐可1,099 / 併用可978 / リモート希望379）。

## 6. 未対応・将来課題
- 3社先以上の深い商流は稀だが汎用N対応済み（数字を正規化してそのまま保持）
- 「プロパー」「プロパー社員」= 自社正社員の別表現。現状は文脈次第。必要なら §2 に追加
- 商流と雇用形態の組合せでマッチング絞り込み（例: 自社のみ・2社先除外）をするなら、この2フィールドをそのまま条件に使える
