① Sheetsリンク: XLSXを本流に、CSVは照合用+保険に降格fetchSheetsEntry設計
  1. CSV取得（export?format=csv&gid=X・軽量）— 役割を変更: 本流のテキストソースではなく、(a) XLSX内で「送信者が指したタブ」を特定するためのgidフィンガープリント、(b) XLSX失敗時の保険テキスト（穴④対策）の2役。
  2. XLSX取得（export?format=xlsx・タイムアウト20秒に統一=穴③対策）— ブック全体が落ちる。バイナリを保持し、後段の統一パイプライン（extractExcelAll）と名簿判定・rels解析（ハイパーリンク検出）の入力にする。Storageアップロード候補にもなる（後段ゾーンE）。
  3. 両方失敗: 警告ログのみで次のリンクへ（現行と同じ）。

gidフィンガープリント照合: エクスポートされたXLSXにはGoogleのgidが含まれないため、gid指定でCSV取得した1タブの内容（先頭数行のセル値）をXLSXの各シートと突き合わせ、一致したシートを「送信者が指したタブ」と認定する（8割以上一致で採用）。実データ検証済み 実リンク（2タブの実経歴書）で19/20一致→正しいタブを選択・B-SHEET-GID発火を確認。実装差分: 前提としてCSVパースを「引用符内の改行・カンマ・\"\"エスケープ」対応の1パス実装にする必要があった — 行分割を先に行う素朴なパーサでは複数行セル（「シメイ↵氏名」等）が壊れ、実データで照合が全滅する（初回実装で実際に発生）。照合不能時はキーワードソートに落ちるだけで悪化はしない。

filenameの補完: エクスポートレスポンスのcontent-dispositionからスプレッドシートの実タイトルを取得し、正規化エントリのfilenameにする（Drive経路の5778-5780行目と同じ手法）。現行のSheets/Docsはラベルが「Googleスプレッドシート(ファイルID)」で人名を含みようがなく、候補者割当のパス1（名前）・パス2（駅名）が構造的に絶対マッチしない非対称があった。タイトルに人名が入っている名簿・個人シート（実務では頻出）でファイル名マッチが初めて機能するようになる。

正規化: 全ソースを統一エントリに揃えるcollectSourceEntries → SourceEntry[]設計の核

メール添付・Drive単体ファイル・Sheets(XLSX)・Docs(DOCX)を、すべて同じ形のエントリに正規化する:

{ bytes, filename, kind: excel|word|pdf|text, origin: attachment|drive|sheets|docs, gidHint?, sourceUrl? }

これで以降の全処理（抽出・名簿判定・候補者割当・Storage保存・resume_url決定）が入力ソースを区別せずに動く。「Sheetsだから」「添付だから」という分岐は正規化より下には存在させない。gidHintとsourceUrlだけがソース固有のメタデータとして残り、シート選択器とresume_url決定でのみ参照される。

bytesを全ソースで保持する意味: 現行はDrive/Sheets/Docs由来のエントリがattachment（元バイナリ）を持たず（6819行目コメント）、複数人材のケースB判定t.attachment?.data（6938行目）を絶対に通れない＝テキストとして本人に割り当てられてもresume_urlの根拠には永遠になれない非対称があった。正規化で全ソースがbytesを持つため、Storage保存・resume_url候補の資格が入力経路に依らなくなる。

氏名照合ゲート（単一人材でも通す）gateSingleCandidate設計

単一人材でもゾーンCの名簿判定は全エントリが通過済み（名簿はここに来る前に行展開されている）。その上で各エントリに軽量な氏名照合ゲートを設ける:

  1. 本人の氏名（またはイニシャル）がエントリのfilename/contentに含まれる → 本人に割当（現行の暗黙動作を明示的に確認）
  2. 本人の氏名が無く、別人の氏名だけが明確に検出される → 本人に紐づけず、名簿展開由来なら新規候補者ブロックとして起こす。それ以外は診断ログ（unattributedEntries）へ記録し、skillYears・resume_urlの根拠から除外

T-3. 不変条件チェック（サイレント失敗の検出器）ledger.checkInvariants設計・今回のバグ群を直接狙う

ゾーン境界で「設計上ありえないはずの状態」を検査し、違反したらINV-*コードで台帳とログに記録する（処理は止めない）。今回の議論で見つかったバグはすべて不変条件違反として書ける:

  • INV-C-MULTI: ゾーンC通過後のエントリに氏名フィールド組が2セット以上残っている（名簿判定のすり抜け）
  • INV-D-DUP: 同一エントリが2人以上のブロックに割当（usedフラグ破り）
  • INV-E-BODYLINK-SKIP: 本人に解析成功エントリが割当済みなのにresume_urlが本文リンク（F.Kさんのバグの再発検知そのもの）
