AIフォールバック詳細設計書
スキル年数エンリッチ（自前HF Space）

ルールで取れなかったスキル年数を、登録後に非同期でAIが埋める仕組みの完全設計。完全無料（API課金ゼロ）・PII外部提供なし・メール処理への影響ゼロを設計制約とし、状態遷移・冪等性・ロック・検証・障害モード・容量・テスト・ロールアウトまで全て定義する。Excel読み込みフロー図の「段階4・4段目」の詳細版。

1. 目的と非目標

目的: ルール抽出（2方式+保険2段）で実スキル年数が0件になった候補者に対し、保存済みの経歴書テキストをAIに読ませてスキル年数を補完する。初見フォーマットの取りこぼしを構造的に減らす。1日あたりの対象件数は未実測（402制限中のため）— 本設計は需要を仮定せず、§11のシナリオ設計と§15の実測ゲートで成立性を担保する。

非目標（やらないこと）:

  • メール処理パイプライン（inbound-email）の変更 — 1行も触らない
  • ルール抽出の置き換え — ルールが本流のまま。AIは空欄の後追い補完のみ
  • 文字のないスキャンPDF・画像のOCR — テキストが無いものは対象外
  • 既存の品質チェック機能（/run_quality_check）の改修 — 独立させる
2. 設計制約（ユーザー合意事項）
制約設計での担保
完全無料HF Spaces無料枠の自前Space + 既存hf-proxy。APIサービス不使用（オープンモデルをセルフホスト）。Gemini等の従量APIは一切呼ばない
PIIを外に出さない経歴書テキストは Supabase ↔ 自前Space 間のみをHTTPSで往復。第三者APIに送らない・Space側でテキストをログに残さない
メール処理を遅くしない完全非同期。登録は今のまま完了し、後からcronが埋める
間違いを混ぜない検証層（§7）を通過した値のみ書き込み。検証落ちは全部捨てる
流量3,000通/日でも成立需要（年数空の登録件数/日）は未実測。§11で最悪シナリオ（全3,000通が対象化）までの挙動と対処を定義し、§15で実測してからパラメータ確定・有効化する

本設計は「inbound-emailはAI不使用」方針の例外を1箇所追加するもの（指定箇所リストに「スキル年数エンリッチ（自前HF Space・非同期）」を追記する）。

4. アーキテクチャ — Pull型を採用設計の核 
pg_cron（10分おき） 既存パターン
  │  net.http_post
  ▼
hf-proxy（Edge Function・既存） ?action=enrich を追加
  │  x-api-secret付きでSpaceを起こす（コールドスタート対応済み）
  ▼
自前HF Space  POST /run_enrich 新設
  │  ① 即座に {ok, started} を返す（202相当・プロキシを待たせない）
  │  ② BackgroundTask で以下を実行（Spaceには実行時間制限が無い）
  ▼
Space内バックグラウンド処理
  1. ロック確認（多重起動なら即終了）
  2. Supabaseから対象候補者を最大3件取得（§5の選定条件）
  3. 各候補者: aiEnrich.status='processing' マーク
       → LLM抽出（Qwen2.5-1.5B・§6）
       → 検証層（§7）
       → 書き戻し + ai_logs記録
  4. 8分経過で残りを次回cronに委ねて終了

Push型（新Edge FunctionがSpaceを呼ぶ案）を却下した理由: Edge Functionには実行時間制限（壁時計150秒）があり、LLM推論40〜90秒/件を待つと1呼び出し1件が限界で、リトライ・タイムアウト管理が複雑化する。Pull型ならSpace側に時間制限が無く、SupabaseアクセスもSpaceが既に持つ資格情報で完結。新しいEdge Functionを作る必要がなく、可動部品が増えない。

5. データ設計 — 対象選定・状態機械・冪等性・ロック隙のなさの核①

対象選定クエリ（毎回実行・キューテーブルは作らない）

candidates から次の全条件で古い順に最大3件:
  ・data_env = 'prod'                     デモ環境は対象外（テスト汚染防止）
  ・created_at ≥ now() − 6日              7日でアーカイブされる前に処理
  ・duplicate_flag = false / merged_into IS NULL
  ・raw_profile->attachmentText が存在     読む文字が無ければ対象外
  ・raw_profile->skillYears に実スキルキーが無い（_内部キーのみは対象）
  ・raw_profile->aiEnrich->status が 'done'/'skipped' でない
  ・aiEnrich->attempts < 3
  ・aiEnrich->lastAt < now() − 2時間       失敗直後の連続再試行を防ぐバックオフ

キュー専用テーブルを作らない理由: 状態はraw_profile.aiEnrich（下記）に持たせれば選定クエリだけでキューが表現でき、スキーマ変更ゼロ・アーカイブ時も状態が一緒に移動する。

状態オブジェクト raw_profile.aiEnrich

{ status: 'processing' | 'done' | 'failed' | 'skipped',
  attempts: number,        モデル起因の失敗のみカウント（§9）
  lastAt: ISO文字列,
  model: 'qwen2.5-1.5b-q4',
  added: {スキル名: 月数},   採用された分（監査用）
  rejected: number,         検証で捨てた件数（品質観測用）
  reason?: string }         failed/skippedの理由

状態遷移

（未処理・aiEnrichなし）
   │ 選定される
   ▼
processing ──成功──▶ done（以後、選定されない）
   │                  採用0件でも done（「読んだが無かった」も確定情報）
   ├─モデル失敗（JSON壊れ・検証全滅3回目）──▶ failed（選定されない・監視対象）
   ├─テキスト無し/短すぎ ──▶ skipped
   └─通信失敗・タイムアウト ──▶ 状態を戻す（attempts消費なし・次回cronで再試行）

冪等性・競合の担保

  • 二重処理防止: 書き込み直前に候補者を再読込し、実スキル年数が既に入っていたら（再解析等との競合）書き込まず done(reason=race) にする
  • 上書き禁止: AIは「空欄を埋める」だけ。既存の実スキル年数を書き換える経路は存在しない（§8 INV-AI-OVERWRITE）
  • 多重起動防止: Space内のグローバルロック（処理中フラグ+開始時刻）。TTL15分 — プロセスが死んでも次のcronで自動回復。cron間隔10分 < TTLなので通常は重ならない
  • processingで固まった場合: lastAtが2時間超過すれば選定条件に再合致して自動復帰

モデル導入（本設計で初めてLLMが実際に動く）

  • Qwen2.5-1.5B-Instruct Q4_K_M（GGUF・約1.0GB） — 無料枠16GB RAMに余裕。0.5Bは抽出タスクには弱すぎるため昇格
  • requirements.txt に llama-cpp-python を追加（現状欠落＝LLM未稼働の原因）
  • 推論設定: temperature=0（毎回同じ答え）・最大出力256トークン・JSONグラマー強制（llama.cppの機能で出力を機械的にJSON形式に制限 — 「JSONで返して」というお願いではなく文法レベルの強制）

入力の決定（v1.2で二段構えに変更 — DBの加工済みテキストに依存しない）

対象候補者
  │
  ├─ resume_url が Storage の .xlsx/.xls？
  │    Yes → 本流: 元ファイル再取得 + セル位置付き生データ
  │      SpaceがStorageから元ファイルをダウンロード
  │      → openpyxl で結合セル（rowspan/colspan）付きセル一覧を再生成
  │      → セル位置付きテキストに整形してLLMへ:
  │           [行3, 列2-4] 品川駅
  │           [行4, 列2]   年齢
  │           [行4, 列3-4] 45歳
  │      LLMは表の位置関係から構造を推測できるため、
  │      ラベル辞書に依存する状態機械の弱点（値の飲み込み・誤ペア）を丸ごと迂回する
  │
  └─ No（Word・PDF・Storage外URL）
       → 保険: attachmentText（文章・先頭3,000字）

なぜDB保存済みのテキストを本流にしないか: DB内の attachmentText（文章化）と jsonRows（構造化）はどちらも抽出パイプラインの加工を経ており、実データで誤ペア（「氏名：保有技術」）・値の飲み込み（「最寄駅＝品川駅年齢45歳」のような結合）が確認されている。壊れた入力を読ませればAIも壊れた答えを返す。元ファイルからの再生成なら加工バグを一切経由せず、attachmentTextの5,000字・上位3シート制限も受けない。

SpanCell再生成をPython（openpyxl）で書き直すことについて: 結合セルの展開は機械的処理（ヒューリスティック無し）のため、TypeScript版（worksheetToCells）との二重管理リスクは実質ない。約30行。requirements.txt に openpyxl を追加する。

プロンプト仕様

入力: セル位置付きデータ（先頭400セル目安） または 文章3,000字
指示: 「Excelのセル位置付きデータ（[行,列範囲] 値）です。位置関係を読んで
      スキル名→経験月数を JSON {"スキル名": 月数} で。
      記載から確実に読み取れるものだけ。推測禁止。無ければ {}」
出力例: {"Java": 60, "AWS": 24, "PostgreSQL": 36}

skill_masterの候補リストをプロンプトに入れない理由: リストを見せると「リストに合わせて答えを作る」誘導（幻覚）が起きる。照合は書き込み前の検証層（§7）で機械的にやるので、モデルには自由に読ませて検証で絞る方が安全。

7. 検証層 — 書き込んでよいものの定義隙のなさの核② 
LLM出力（JSON文字列）
  │ ① 厳格パース: JSONとして壊れていたら全捨て（attempts+1）
  ▼
  │ ② スキル名検証: skill_master の name / aliases に正規化一致
  │    （小文字化・空白除去。Space起動時ロード済みの約1,660件と照合）
  │    一致しないキーは個別に捨てる（rejectedカウント）
  ▼
  │ ③ 月数検証: 整数化できない・0以下・360超 は捨てる（360=30年でキャップ）
  ▼
  │ ④ 直前再読込: 実スキル年数が既に入っていたら中断（競合防止）
  ▼
書き込み（1候補者につき1回のUPDATE）:
  ・raw_profile.skillYears ← 検証済みの値（skill_master正名で格納）
  ・raw_profile.aiEnrich ← done + added/rejected
  ・raw_profile.pipeline_trace.emailCodes へ "E-SY-AI(n件採用/m件棄却)" を追記
  ・candidates.skills 配列へ未収載スキルを追加 + candidate_skills へINSERT
     （inbound-emailが登録時にやっている「skillYears→skills反映」と同じ規則）
  ・experience_years が null の場合のみ、月数から推定して補完
  ・ai_logs へ1行INSERT（model='hf-qwen2.5-1.5b', linked_id=候補者ID）
     （既存のAIコスト・品質監視の枠にそのまま乗る）
8. 不変条件（違反したらバグ）
  • INV-AI-OVERWRITE: 実スキル年数が入っている候補者のskillYearsをAIが変更することは無い（選定条件+書込前再読込の二重防御）
  • INV-AI-UNVALIDATED: skill_masterに存在しないスキル名がAI経由で書き込まれることは無い
  • INV-AI-DEMO: data_env='demo' の候補者にAIが書き込むことは無い（E2Eテストの期待値を汚さない）
  • INV-AI-TRACE: AIが書き込んだ候補者には必ず aiEnrich と E-SY-AI が残る（後から「どれがAI由来か」を100%特定できる）
9. 障害モード表 — 全部の「壊れ方」と挙動隙のなさの核③
障害挙動attempts
Spaceがコールドスタート中hf-proxyが25秒×4リトライで起こす（既存実装）。起きなければ次の10分後cronへ—
Space再起動でロック消失ロックはメモリ上のため消える＝次のcronが正常に取得。processing残骸は2時間バックオフ後に自動再選定消費なし
Supabase接続失敗（402含む）バッチ全体を中断。候補者の状態は変更されない → 次回そのまま再試行消費なし
Storageから元ファイルの取得失敗attachmentText（文章）に降格して続行。トレースに記録—
元ファイルが巨大（名簿等）セル数上限（先頭400セル目安）で切ってLLMへ。超過をトレースに記録—
xlsxが破損していて開けないattachmentTextに降格。それも無ければ skipped—
LLM出力がJSONとして壊れたグラマー強制で原則発生しないが、発生時は全捨てして attempts+1。3回で failed+1
LLMが妄想スキルを出したskill_master照合で機械的に棄却（rejected計上）。採用0件でも done（正常終了）—
推論が異常に長い1件あたり180秒のハードタイムアウト → 通信失敗扱い。バッチ全体は8分予算で打ち切り消費なし
再解析と同時実行（競合）書込前再読込で検出 → 書き込まず done(reason=race)—
7日以内に処理が追いつかずアーカイブ対象から自然に消える（未補完のままアーカイブ）。容量16倍の余裕があるため通常起きない。発生率は監視で観測—
HF無料枠の仕様変更・停止エンリッチが止まるだけ。登録済みデータには一切影響なし（このシステムの他の機能から完全に独立）—
モデルが劣悪な結果を量産ai_logs と aiEnrich.added が全件監査可能。app_config で即時停止＋AI由来分は E-SY-AI で特定して一括巻き戻し可能—
10. セキュリティ・プライバシー
  • 認証: 既存の x-api-secret（Space側Secrets）。secretなしのアクセスは全拒否
  • 経路: Supabase ↔ 自前Space のHTTPSのみ。第三者API・外部サービスへの送信なし
  • Space側で経歴書テキストをログに出力しない（文字数のみログ可）。ディスク保存もしない（メモリ処理のみ）
  • HF Spaceはprivateリポジトリにする（コード内にSupabase URLが含まれるため）。Secretsは HF Spaces の Secrets 機構で管理（コードに書かない）
  • 自前Space内のセルフホスト推論のため、入力データが第三者のモデル学習に使われる経路が存在しない
11. 性能・容量 — 需要は未実測。だから「未知でも成立する」設計にする要実測2項目あり

正直な前提: 本番の需要（=年数空で登録される件数/日）は402制限中で測れていない。参考値（登録約130件/日 × テストセットのルール失敗率3割 ≈ 40件/日）は推定×推定であり、設計の根拠にしない。設計は「需要がいくつでも壊れない」ことを示し、実数は§15のゲートで確定する。

供給の物理天井（ここだけが確かな数字の枠組み）

Space内の処理は直列（1プロセス・ロック§5）なので、日次の絶対天井は:

    天井 = 86,400秒 ÷ T   （T = 1件の処理秒数・要実測①・想定40〜90秒）

    T=90秒 → 約  960件/日
    T=60秒 → 約1,440件/日
    T=40秒 → 約2,160件/日

cron間隔・バッチ数はこの天井内での「呼び出し方」にすぎない:
    初期値 10分おき×3件 = 432件/日（意図的に天井より絞った安全運転）
    ノブ: バッチ6件 or 5分間隔 → 天井近くまで増強可（コード定数の変更のみ）

需要シナリオ表 — いくつ来ても挙動が定義されている

需要/日挙動
〜400件初期値（432件/日）のまま当日中に消化。設定変更不要
〜900件ノブ増強（バッチ/間隔）で天井内。T=90秒の悲観値でも収まる
〜2,000件T実測が60秒以下なら天井内。超えるなら入力字数削減（3,000→2,000字）でTを短縮 or Space並列化（無料で複数Space可・候補者IDで分担）
3,000件（受信全通が対象化する理論上限）1 Spaceでは不足。ただしこの状態は「全メールが年数空candidateとして登録されている」ことを意味し、それ自体が誤登録監査(audit_misregistration)で対処すべき異常。エンリッチ側は下記の溢れ政策で安全に部分処理

溢れたときの政策（供給<需要でも壊れない）

  • 優先度: 新しい順に処理（営業は新着から当たるため補完価値が高い。§5の選定を created_at DESC に変更）
  • 処理が7日以内に届かなかった候補者は未補完のままアーカイブへ — 欠けるのは「AIによる上乗せ」だけで、登録・検索・経歴書ボタン・ルール抽出分は無影響
  • 未処理率は監視（§13）で観測し、恒常的に高ければノブ増強 or Space並列化を発動

要実測（§15のゲートで確定するまで有効化しない）

  1. T（1件の処理秒数）: 無料枠2vCPU上の実測。ローカル検証と初回ビルド後にSpaceで計測
  2. 需要/日: 7/23復旧後に monitor_quality.mjs のBチェック（添付ありskillYears空）を数日観測して確定

14. テスト計画と受入基準
