AIフォールバック設計 — 平易版

AIが「スキル年数の空欄」を
後から埋める仕組み

経歴書からスキルの経験年数がルール（プログラム）でうまく取れなかったとき、あとからAIが読み直して埋めてくれる新機能の設計。専門用語をできるだけ減らして「何を・なぜ・どう」だけをまとめた。

これは平易版。実装の合意・仕様の細部（状態遷移・障害時の挙動・容量計算など）は ai-enrich-design-v1.2.html（詳細設計書）が正式版。
処理ステップ 安全のための仕組み まだ分かっていないこと・弱点
3行でいうと
  1. 今のルール（プログラム）では、経歴書の書き方が変わっていると「スキル：何年経験」が読み取れないことがある
  2. その空欄を、候補者登録の後で・裏側でこっそりAIが経歴書を読み直して埋める（メールの処理自体は今のまま・1秒も遅くならない）
  3. AIは無料の自前サーバー（Hugging Face Spaces）で動かす。お金はかからず、経歴書のデータも外部の会社には送らない
なぜ必要か

今の仕組みは「よくある書き方」を覚えたルールでスキル年数を読み取っている。ところが経歴書のフォーマットは会社ごと・人ごとにバラバラで、見たことのない書き方だと0件になる。ルールを1件ずつ直して対応する今のやり方（週次の改善ループ）は効果があるが、追いつかない書き方が必ず残る。

AIは「決まった形式」ではなく内容を読んで理解するため、初めて見る書き方でもある程度読み取れる。ルールを置き換えるのではなく、ルールが取れなかった分だけを後から拾う保険として使う。

絶対に守る4つの約束
約束どう守るか
お金がかからないChatGPTのような有料APIは使わない。無料で使える自前サーバー上でAIモデルを動かす
個人情報を外に出さない経歴書の中身は自社のサーバーの中だけで処理する。外部の会社のAIサービスには一切送らない
メールの処理を遅くしない候補者の登録は今まで通りすぐ終わる。AIは登録が終わった後で裏側で動く
間違った情報を混ぜないAIの答えをそのまま信じない。「本当に実在するスキル名か」「年数がおかしくないか」を機械的にチェックしてから、通ったものだけを反映する

どう動くか（全体の流れ）

10分おきに「様子見」に来て、空欄を見つけたら埋める 
1. メールが届く → いつも通り候補者を登録（スキル年数が空欄でもそのまま登録される）
                        │
2. 10分おきに、自動で「スキル年数が空欄の候補者、いない？」と確認しに行く
                        │
3. 見つかったら（1回につき最大3人まで）、保存してある経歴書ファイルを
   AI（自前サーバー上のAIモデル）にもう一度読ませる
                        │
4. AIの答えをそのまま信じず、機械的なチェックに通す（次のブロック参照）
                        │
5. チェックを通った分だけ、候補者の情報に追記する

なぜ「登録後にこっそり」なのか: AIに経歴書を読ませるのは数十秒〜数分かかることがある。メールが届いた瞬間にAIを待たせると登録全体が遅くなってしまうため、登録は先に終わらせて、AIは後から追いかける形にしている。

ファイルの取得先を決める優先順位

候補者テーブルに保存されたURL情報から、どれを使うか

メール登録時に、候補者の resume_url / box_url / drive_url というカラムにファイルのURL情報が保存されている。AIが読む元ファイルはここから取得する：

【第1優先】resume_url が Supabase Storage 内の Excel ファイル？
  └─ YES → Storage からダウンロードして再読み込み（推奨）
             元ファイルそのものなので、メール処理時の加工を経ていない
             →表の構造がそのままAIに渡る

【第2優先】resume_url に Google Drive リンク や Word ファイル？
  └─ YES → DB に保存済みの「テキスト化版」（先頭3,000字）を使う
             ※ Storage ダウンロード失敗時の保険にもなる

【第3優先】box_url に Box 共有URL あり？
  └─ 別処理で Box → Google Drive に転送（box-downloader）
     転送後は drive_url として記録される

なぜ優先順位がこうなっているか: Supabase Storage の元ファイル（Excel）が最優先なのは、メール処理時の「テキスト化」の過程で「氏名：保有技術」のようなおかしなペアが混ざってしまう弱点が発見されているため。元ファイルをもう一度開き直せば、その加工を経由せず、表の位置関係をそのままAIに読ませられる。

AIは何を読むのか

できるだけ「元のExcelファイル」を読み直すv1.2での変更点

登録時にすでにテキスト化された文章をAIに読ませることも考えたが、そのテキスト化の過程で「氏名：保有技術」のようなおかしなペアができてしまうことが分かっている（元々の弱点）。壊れた文章をAIに読ませても、AIも間違えてしまう。

そこでv1.2では、保存してある元のExcelファイルをもう一度開き直して、セルの位置関係が分かる形でAIに渡すことにした。表の縦横の並びをAI自身に判断させることで、テキスト化の際の誤りを回避できる。Excel以外（Wordなど）の場合は、これまで通りのテキスト（先頭3,000字）を読ませる。

使うライブラリ: Python の openpyxl（AIサーバー側で新たに追加する）。今のメール処理（TypeScript・xlsxライブラリ）とは別物で、AIサーバーが独自に元ファイルをダウンロードして開き直す。「結合されているセルを本来の広がりに展開する」という機械的な処理だけを行うので、今のメール処理側のロジックと二重管理になる心配はほぼない。

AIに渡すデータの中身（セル位置付きテキスト）: ふつうの文章ではなく、「どのマス目に何が書いてあるか」を1行ずつ並べたテキスト。例えば経歴書の一部が下のような表だった場合:

[行3, 列2-4] 品川駅
[行4, 列2]   年齢
[行4, 列3-4] 45歳

「行3の列2〜4（横に結合された1マス）に"品川駅"」「行4の列2に"年齢"」「行4の列3〜4に"45歳"」という意味。ふつうにテキスト化すると年齢45歳のようにくっついて読み間違えやすい部分も、位置情報が残っていればAIが表の構造として正しく解釈しやすくなる。渡すのは先頭400マス分程度まで（大きすぎる名簿ファイル対策）。

間違った情報を混ぜない仕組み（いちばん大事な部分）

AIの答えは「候補」でしかない。3段階でふるいにかける
  1. 形式チェック: AIの答えがきちんとしたデータ形式になっているか（壊れていたら丸ごと捨てる）
  2. 実在チェック: 出てきたスキル名が、社内で管理している約1,660件のスキル一覧に実在するか（一覧にない名前は個別に捨てる。AIが存在しないスキル名を答えてしまう「幻覚」への対策）
  3. 数値チェック: 経験月数が明らかにおかしい数字（マイナス・0・30年超など）でないか

3つとも通った分だけ、候補者の情報に書き加える。既にスキル年数が入っている項目をAIが上書きすることは絶対にない（空欄だけを埋める）。誰がいつAIで埋めたかも記録に残すので、後から見返して間違いに気づけば取り消せる。

動かなくなったらどうなるか

この仕組みが止まったり失敗したりしても、すでに登録されているデータには一切影響しない。困るのは「AIによる上乗せが増えない」というだけで、登録・検索・経歴書ボタンなど他の機能はいつも通り使える。

起きること結果
AIサーバーが一時的に止まっている次の10分後にまた挑戦する。手動対応は不要
AIが変な答えを返すチェックで機械的に弾かれる。何も書き込まれない
処理が終わらないまま固まる2時間で自動的にリセットされ、また挑戦できる状態に戻る
思ったより効果が悪い設定を1つオフにするだけで即座に停止できる（緊急停止スイッチ）。データは無傷
どれくらいの量をさばけるか — 正直、まだ分からない実測してから本稼働

「1日に何人分の空欄が発生するか」はまだ実測できていない（別件の制限中のため）。ただし1人読むのに40〜90秒かかるとしても、1台のAIサーバーだけで1日あたり1,000件前後は処理できる計算になっている。仮に想定を超える量が来ても「新しい候補者から優先して処理する」「サーバーをもう1台増やす」といった対処法をあらかじめ用意してある。

数字が読めない状態でいきなり本番稼働はしない。まず実際の空欄発生数と処理時間を数日間観測し、それに合わせて頻度を調整してから有効化する、という順序を踏む。

導入の進め方（いきなり全部は動かさない）
  1. まずAIサーバー側だけを作って、手元のテストデータで正しく答えられるか確認する
  2. 本番環境に配線（10分おきの自動チェック）だけ入れるが、スイッチはオフのままにする — この時点では1件も動かない
  3. 数日間、実際にどれくらい空欄が発生するか観測する
  4. 観測結果をもとに頻度を決めて、1件だけ手動で試し、結果を目視確認する
  5. 問題なければスイッチをオンにして本稼働。その後も1週間は結果を見張る
残る弱点（正直に）
  • 使うAIモデルは小型（軽量版）なので、複雑な経歴書だと読み取れないことがある。ただし「間違って埋まる」ことはなく「取れる分だけ増える」だけなので、悪化はしない
  • 社内のスキル一覧にまだ登録されていない新しい技術名は、実在チェックで弾かれてしまい拾えない（一覧の定期メンテで対応）
  • 文字が入っていないスキャンPDFや画像の経歴書は、そもそも読む文字がないので対象外のまま
