## 1. 設計方針

正規化後の文字列に対し、**マーカー文字（都/道/府/県・線・駅）で終わる部分文字列をスキャンして抜き出す**方式にすれば、**スペース・順序は結果に影響しない**（「本厚木駅 神奈川県」でも「神奈川県本厚木駅」でも同じ抽出結果になる）。
そのため表の軸から「順序」を外し、**各成分（県・線・駅）の表記状態（マーカーあり／マーカーなしの素名／存在しない）**を軸にする。

## 3. 同名駅の曖昧性解消（線データが必要な部分）

| 状況 | 線データの有無 | 挙動 |
|---|---|---|
| 駅名が全国一意（例: 本厚木） | 不要 | 駅名だけでDB照合すれば確定 |
| 駅名が同名で複数県に存在（例: 府中・橋本・本町） | **線があれば** | 「駅名＋線」の組でDB照合 → 一意に確定 |
| 同名駅かつ線も取れない | なし | 推測せず null（誤登録より欠損の方が安全という既存方針と一致） |

## 4. フィールド内抽出 と 複数ソース間の優先順位の違い（重要な注意）

本設計書の §2 は「**最寄駅という1フィールド内**での県/線/駅の抽出」の話。
一方、実際の候補者データ確定処理（index.ts 9206-9213行目付近）では、**複数のソース（AI抽出・住所ラベル・全文検索・駅名DB照合）の間の優先順位**が別途存在し、そちらは:

```
resolvedPrefecture = AI結果 || regex結果(住所ラベル/全文検索) || 駅名DB照合
↓
駅名DB照合の結果が上記と食い違う場合は駅名DB照合が最終的に上書きする
```

つまり「本文中の県表記」と「駅名から引いた県」が食い違う場合、**最終的には駅由来が勝つ**（送信者署名の別住所を駅名で正しく上書きするための既存設計）。表2のケース#1「県マーカー最優先」はフィールド内抽出の設計であり、この複数ソース間の優先順位とは別レイヤーである点に注意。

## 6. 線データの導入（2026-07-25 解決）

`station_master` は当初 `id / name / prefecture / created_at` のみで路線データを持たず、8,685件の駅名は全てユニークに潰れていた（例: 「府中」は東京都のみ登録され、広島県・徳島県の府中駅は欠落）。

**対応**: ユーザーが ekidata.jp（駅データ.jp）で会員登録の上、駅マスタ・路線マスタCSVをダウンロード。実データをスクリプトで変換（AI生成ではなく機械的な変換）し、`station_master` に `line` 列を追加した上で全面再シード。

- 出典: ekidata.jp（2026年7月ダウンロード分）
- マイグレーション: `supabase/migrations/20260725_station_master_add_line.sql`
- 結果: 12,666行（8,443ユニーク駅名）。「府中」は広島県(JR福塩線)・徳島県(JR徳島線/よしの川ブルーライン)・東京都(京王線) の4行として正しく分離登録
- 同名駅の判別ロジック: 入力に路線名が含まれていれば一致する行の都道府県を採用。路線名が取れず複数県にまたがる場合は**推測せずnull**（誤登録より欠損の方が安全という既存方針を踏襲）

実例（MEさん・2026-07-24処理）: 「小田急小田原線本厚木駅」→ 神奈川県（本厚木は全国で一意なので線なしでも解決）。既存レコードは手動で `raw_profile.prefecture` を修正済み。
