同じ「PMO」ラベルが付いた2人の中身:

| 希望 | 経歴書の中身 | 付いた役割 |
|---|---|---|
| 160万 | 大手金融・官公庁のPMO支援。RFP〜ベンダ評価選定、AsIs/ToBe整理 | PMO, コンサルタント, PM, 運用保守 |

**この2人が同じ点数になる。** 原因は、うちが役割を「ラベル1本」で持っているから。

権威ある枠組みは**例外なく「役割 × レベル」の2次元**である:

| 枠組み | 役割の軸 | レベルの軸 |
|---|---|---|
| SFIA（英国・ITSSのレベル設計の元） | 各スキル | **7段**（自律性・影響範囲・複雑さで決まる。スキル名では決まらない） |
| IPA ITSS | 11職種35専門分野 | **7段** |
| 日本PMO協会（NPMO） | PMO | **3職種**（アドミニストレータ／エキスパート／マネジャー） |
| PMI | PMO | **3型**（supportive／controlling／directive） |
| **AkiNavi（現状）** | 19ラベル | **なし** |

レベル軸が無いことが、PowerPoint上級の人と官公庁のRFP評価をやった人を同一視している原因。

## 1. 定義の原理（3軸）

役割を「名前」ではなく「**何に・どれだけの権限で・どこまで到達して**働きかけたか」で定義する。

### 軸1: 作用対象 — 何に働きかけるか

日本PMO協会の定義がそのまま原理になる:
> プロジェクトマネジャーは「プロジェクト」のために活動する。PMOは「プロジェクトマネジメント」のために活動する。

対象が違うのだから、PMとPMOは近くない。これを5つに一般化する。

| 対象 | 意味 |
|---|---|
| **事業** | 顧客の経営・業務そのもの |
| **成果** | このプロジェクトのQCD（品質・コスト・納期） |
| **仕組み** | プロジェクトを回す型（標準・見える化・課題管理の枠組み） |
| **製品** | 作られるシステム・ソフトウェアそのもの |
| **サービス** | すでに稼働しているサービスの継続提供 |

### 軸2: 権限 — どこまで自分で決められるか

SFIAの原則（レベルを決めるのはスキル名ではなく autonomy / influence / complexity）を4段に圧縮。

| 権限 | 定義 |
|---|---|
| **L4 決裁** | 予算・契約・要員・納期を自ら決め、その結果に責任を負う |
| **L3 統率** | 他者に作業指示を出し成果物の可否を判断する。ただし予算・契約の決裁権はない |
| **L2 実行** | 与えられた範囲の成果物を自ら作る。判断は自分の担当範囲内 |
| **L1 支援** | 他者の活動を成立させる。他者の作業内容を自分の判断では変えられない |

### 軸3: 到達レベル — その役割をどこまでやったか

**新設。これが「見抜く」の実体。** 同一ラベル内をNPMOの3層と同じ粒度で分ける。

| 到達 | 定義 | 判定の根拠 |
|---|---|---|
| **A 主導** | その役割を単独で回した。他者・他社を動かした。組織横断・標準策定・対外交渉 | 本文にA級語がある |
| **B 担当** | その役割の中核作業を任されて回した | B級語がある |
| **C 従事** | 周辺作業のみ。チームの一員としての関与 | C級語しかない |
| **－ 裏付けなし** | 役割語はあるが、その役割の業務記述が見当たらない | A/B/C いずれも無い |

#### ⚠ 役割そのものは消さない

当初は「必須裏付けが無ければ役割を落とす」設計にしかけたが、**実測して取りやめた。**
テックリード200人は**全員がカナで「テックリード」と書いており**、略号TLの誤爆はゼロだった。
落とす設計だと、私の裏付け語が狭かっただけで正しい129人を消していた。

役割は残し、**印を付けて営業に見せる**。落とすと根拠が確認できなくなる。

#### 実測: どの役割でレベルが機能するか

直近7日・prod の平均希望単価（万円）。**単価が単調に分かれた役割にだけ印を付ける。**

| 役割 | 付与 | A級 | B級 | C級 | 差 | 採用 |
|---|---|---|---|---|---|---|
| コンサルタント | 129 | **117**(72人) | 99(38) | 74(13) | 43 | ✅ |
| アーキテクト | 81 | **111**(44) | 99(19) | 72(18) | 39 | ✅ |
| PMO | 630 | **97**(256) | 76(243) | 66(42) | 31 | ✅ |
| プロジェクトマネージャー | 685 | **106**(108) | 85(489) | 77(28) | 29 | ✅ |

#### 単価との矛盾を出す

C級（周辺作業どまり）または裏付けなしで**希望80万以上**なら、画面に「単価要確認」を出す。
落とさない。営業が経歴書を見て判断する材料にする。
実測: PMO で C級かつ80万以上が6人、裏付けなしかつ80万以上が26人。

## 2. 役割定義表

19ラベルすべて。**ラベルは増やさない**（DB `role_master` / `scoreProseRoles` の `ROLE_DEFS` /
`project_apply.mjs` の `ROLE_LABELS` / 案件AIプロンプトの4か所と一致させる必要があるため）。

### 2-1. マネジメント・推進

#### プロジェクトマネージャー — 対象:成果 / 権限:L4
- **定義**: プロジェクトの目的の実現に向けて、要求品質・コスト・納期に**責任を持つ**者。
- **根拠**: IPA プロジェクトマネージャ試験 対象者像「プロジェクトの目的の実現に向けて責任をもってプロジェクトマネジメント業務を…担う者」／PMBOK 7th（スチュワードシップ）
- **必須裏付け**: `予算|見積|契約|要員計画|採算|原価|コスト管理|ベンダ|顧客折衝|体制構築` のいずれか
  - 理由: **カネとヒトに触れていないPMは定義上成立しない**。QCDの責任＝金と人の裁量。
- **A級**: `複数プロジェクト|全体統括|◯億|◯千万|役員報告|経営報告|部門横断`
- **降格先**: 進捗・課題管理の記述はあるがカネ・ヒトが無い → **プロジェクトリーダー**
- **実測**: 685人中116人（17%）が必須裏付けなし

#### プロジェクトリーダー — 対象:成果 / 権限:L3
- **定義**: チームに作業指示を出し、進捗と成果物の可否を判断する。予算・契約の決裁権は持たない。
- **根拠**: IPAに試験区分は無い（実務慣行）。PMとの差は**決裁権の有無**の1点。
- **必須裏付け**: `メンバー|レビュー|指示|進捗|チーム|統括|取りまとめ|牽引|後輩|育成` のいずれか
- **A級**: `10名|20名|◯名規模|複数チーム|オフショア`
- **除外**: **サブリーダーはPLではない**（補佐であり、指示権も責任範囲も違う。2026-09-01 修正済み）
- **実測**: 1,043人中105人（10%）が必須裏付けなし

#### PMO — 対象:仕組み / 権限:L1
- **定義**: **プロジェクトマネジメントそのもの**を対象に、標準化・見える化・事務局運営でPMを支援する。
  **プロジェクトの成否に責任を負わない。** 指示権を持たない。
- **根拠**: 日本PMO協会「PMOは基本として"プロジェクトマネジメント"のために活動」／PMI supportive PMO
- **PMとの距離**: 対象が違い（成果 vs 仕組み）、権限も3段違う（L4 vs L1）。**両軸とも最遠**。
  これが「PMとは雲泥の差」の構造的な根拠。従来 0.7 → **0.2**。
- **必須裏付け**: `進捗管理|課題管理|議事録|WBS|会議体|事務局|資料作成|要員調整|工数管理|標準化` のいずれか
- **到達レベル**（NPMOの3職種にそのまま対応）:
  | 到達 | NPMO | 判定語 |
  |---|---|---|
  | A 主導 | PMOマネジャー | `全社|EPMO|複数プロジェクト|横断|標準化|RFP|ベンダ評価|グランドデザイン|経営報告` |
  | B 担当 | PMOエキスパート | `課題管理|リスク管理|進捗管理|工数管理|見える化|プロセス改善` |
  | C 従事 | PMOアドミニストレータ | `議事録|資料作成|日程調整|入退場|アカウント発行|PC手配|備品` |
- **降格先**: 必須裏付けが無い → **役割を付けない**
- **除外文脈**: `PMOと連携|PMO配下|PMO主催|PMOからの指示|PMOに報告` は**他人の役割**
- **実測**: 主役割380人。うち80万以上希望が177人。A級とC級が同一ラベルに同居している。

#### スクラムマスター — 対象:仕組み / 権限:L2
- **定義**: スクラムチームの有効性に責任を持つ。**指示権を持たない**。チームの自己管理を助ける。
- **根拠**: Scrum Guide 2020「accountable for the Scrum Team's effectiveness」「no command authority」
  （2020版で "role" が "accountabilities" に改められた点が重要。PMとは別物）
- **必須裏付け**: `スプリント|バックログ|レトロスペクティブ|デイリー|アジャイル|スクラム` のいずれか
- **A級**: `導入|立ち上げ|複数チーム|組織展開|コーチ`

#### コンサルタント — 対象:事業 / 権限:L3
- **定義**: 顧客の経営・業務課題に対し、あるべき姿と実現手段を提示する。**実行の責任は顧客側**。
- **根拠**: ITSS「コンサルタント」職種
- **必須裏付け**: `提案|RFP|As-Is|ToBe|グランドデザイン|業務改革|BPR|戦略|診断|評価選定` のいずれか
  - 理由: 「コンサルタント」は**肩書きとして最も安く名乗れる語**。成果物の記述を必須にする。
- **A級**: `経営|役員|全社|中期計画|M&A`

### 2-2. 設計・実装

#### アーキテクト — 対象:製品 / 権限:L3
- **定義**: 全体最適の観点から対象システムの構造を設計し、開発を主導する。
- **根拠**: IPA システムアーキテクト試験 対象者像「要件を定義し、それを実現するためのアーキテクチャを設計し、開発を主導する者」
- **必須裏付け**: `アーキテクチャ|方式設計|非機能|全体設計|グランドデザイン|技術選定|基盤設計` のいずれか
- **A級**: `全体最適|マルチクラウド|大規模|標準化|技術戦略`

#### テックリード — 対象:製品 / 権限:L3
- **定義**: 実装しながら技術判断を行い、実装者を技術面で率いる。
- **根拠**: 実務慣行（IPA区分なし）。アーキテクトとの差は**自分も実装するか**。
- **必須裏付け**: `技術選定|コードレビュー|設計レビュー|technical lead|技術リード|技術支援` のいずれか

#### システムエンジニア — 対象:製品 / 権限:L2
- **定義**: 要件定義〜設計〜テストの工程を担当する（技術領域を特定しない汎用ラベル）。
- **根拠**: 日本のSES慣行。**世界標準には対応語が無い**ため、より具体的なラベルが取れるなら常にそちらを優先する。
- **必須裏付け**: `要件定義|基本設計|詳細設計|外部設計|内部設計` のいずれか
- **降格先**: 実装語のみ → **プログラマー**

#### プログラマー — 対象:製品 / 権限:L2
- **定義**: 設計に基づき実装する。設計の責任は持たない。
- **必須裏付け**: 言語名または `実装|コーディング|製造`

#### バックエンドエンジニア — 対象:製品 / 権限:L2
- **定義**: サーバサイドの**インタフェースとデータ構造を設計し**実装する。
- **必須裏付け**: サーバサイド言語（`Java|C#|Python|Go|Node|PHP|Ruby|Kotlin|Scala|Rust`）
  **かつ** `API|REST|GraphQL|gRPC|インタフェース設計|IF設計|テーブル設計|DB設計|スキーマ` のいずれか
  - 理由: **仕様書を書いたことがない実装者は設計者ではない。** 隙のないAPIは、言語の年数と
    インタフェース設計の経験の両方が要る。片方だけならプログラマー。
- **A級**: `性能|認証|認可|スケール|冪等|トランザクション設計|マイクロサービス`
- **降格先**: 言語はあるが設計語なし → **プログラマー**
- **実測**: 50人中11人（22%）が設計語なし

#### フロントエンドエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: `React|Vue|Angular|TypeScript|JavaScript|HTML|CSS|Next` のいずれか
- **A級**: `設計|コンポーネント設計|パフォーマンス|アクセシビリティ|デザインシステム`

#### フルスタックエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: フロント側の語 **かつ** バックエンド側の語（両方が要る）
- **降格先**: 片側のみ → その側のラベル

#### インフラエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: `Linux|Windows Server|ネットワーク|サーバ構築|仮想化|VMware|冗長|監視設計` のいずれか

#### クラウドエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: `AWS|Azure|GCP|Google Cloud|Terraform|Kubernetes|EKS|AKS` のいずれか
- **A級**: `移行|IaC|マルチアカウント|コスト最適化|SRE`

#### データエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: `ETL|データ基盤|DWH|BigQuery|Snowflake|Redshift|データパイプライン|Databricks` のいずれか

#### MLエンジニア — 対象:製品 / 権限:L2
- **必須裏付け**: `機械学習|深層学習|TensorFlow|PyTorch|scikit|LLM|推論|モデル` のいずれか

#### テストエンジニア — 対象:製品 / 権限:L2
- **定義**: 品質の検証に責任を持つ。テスト設計・実行。
- **必須裏付け**: `テスト設計|テスト計画|テストケース|品質|不具合|検証|QA` のいずれか
- **A級**: `テスト戦略|自動化|CI|網羅|品質保証`

### 2-3. サービス

#### 運用保守 — 対象:サービス / 権限:L2
- **定義**: 稼働中サービスの監視・障害対応・定常運用を担う。
- **根拠**: IPA ITサービスマネージャ試験 対象者像「サービスの計画立案、設計、移行、提供及び改善のための組織の活動及び資源を、指揮し、管理する」の実務層
- **必須裏付け**: `監視|障害対応|定常|運用設計|インシデント|一次対応|バッチ|夜間` のいずれか
- **A級**: `運用設計|SLA|改善|自動化|運用標準|指揮`

#### ヘルプデスク — 対象:サービス / 権限:L1
- **定義**: 利用者からの問い合わせを一次受けし、解決するか適切に取り次ぐ。
- **根拠**: ITSS「カスタマーサービス」職種
- **必須裏付け**: `問い合わせ|一次受け|一次対応|ユーザーサポート|キッティング|アカウント|マニュアル` のいずれか

## 3. 近さ（role_affinity）の算出

**恣意的な値を置かない。2軸から式で出す。**

### 対象距離

|  | 事業 | 成果 | 仕組み | 製品 | サービス |
|---|---|---|---|---|---|
| **事業** | 0 | 1 | 2 | 1 | 2 |
| **成果** | 1 | 0 | 1 | 1 | 2 |
| **仕組み** | 2 | 1 | 0 | 2 | 1 |
| **製品** | 1 | 1 | 2 | 0 | 1 |
| **サービス** | 2 | 2 | 1 | 1 | 0 |

距離1とした根拠:
- 事業↔成果: コンサルの提案がそのままプロジェクトになる
- 事業↔製品: アーキテクトは事業要件を構造に落とす
- **成果↔仕組み: NPMOの定義そのもの（PMOはPMの活動を対象にする）**
- 成果↔製品: PLは成果物を通じて成果を出す
- 製品↔サービス: 作ったものが運用に渡る
- 仕組み↔サービス: どちらも「回し続ける」支援業務

### 式

```
対象係数 = 距離0→1.0 / 1→0.6 / 2→0.35
権限係数 = 差0→1.0 / 1→0.75 / 2→0.5 / 3→0.3

affinity = clamp(対象係数 × 権限係数, 0.2, 0.9)
  ただし 同一ラベル = 1.0、どちらか不明 = 0.5
```

下限0.2は据え置き（2026-08-14 ユーザー判断「ゲートではない。系統違いでも0.2は残す」）。

### 主要ペアの結果

| 要求 | 人材 | 新 | 旧 | 変化の理由 |
|---|---|---|---|---|
| PM | **PMO** | **0.2** | 0.7 | 対象も権限も最遠。**これが今回の主目的** |
| PM | PL | 0.75 | 0.7 | 対象同じ・権限1段差 |
| PM | SE | 0.30 | 0.2 | 対象隣接・権限2段差 |

| PMO | 運用保守 | 0.45 | 0.7 | 権限1段差 |
| PMO | スクラムマスター | 0.75 | 0.7 | 対象同じ（仕組み） |

## 4. 「見抜く」のは誰の仕事か

| 判定 | 担当 | 状態 | 理由 |
|---|---|---|---|
| **到達レベル A/B/C/－** | **regex** | ✅ 実装済 | 語彙が距離を持つので機械的に決まる。費用ゼロ。実測で6役割が単調に分離 |
| **単価との矛盾**（C級・裏付けなしで80万以上） | **regex** | ✅ 実装済 | 数値比較。画面に「単価要確認」を出す |
| **他人の役割**（「PMOと連携」「PMO配下」） | **regex** | 未 | 文型が固定。実測2件と少ない |
| **A級語が本人の実績か案件説明か** | **AI** | 未 | 「全社標準化のプロジェクトに参画」は全社標準化を"した"とは限らない |
| **経歴の深さ**（言語5年の実質、設計の質） | **AI** | 未 | 年数の申告と記述内容の整合を読む必要がある |
| **分離しなかった6役割の語彙改善** | **人** | 未 | バックエンド・運用保守・ヘルプデスク・テスト・SE・PL |

**AIは最後の一段だけ。** レベル判定そのものはregexで足りることが実測で分かった
（費用ゼロ・監査可能・即日）。AIに回すのは「書いてあることが本人の実績か」の判断だけ。

### 案件側は肩書きに引きずられる（2026-09-02・実求人でA/B検証）

ユーザーが持ち込んだ実求人「長期案件PMOコンサル・月100〜160万」（業務委託）。
職務内容は As-Is/To-Be整理、RFP作成支援、ベンダー選定、スコープ定義、
品質・コスト・スケジュール管理、WBS管理、運用設計。

同じ本文を新旧のプロンプトで解釈させた結果（`interpret_text.mjs` で再現できる）:

| | requiredRole | AIの理由 |
|---|---|---|
| 旧 | **PMO** | 「プロジェクト推進・WBS管理・品質・コスト・スケジュール管理などの**進行管理**が主務」 |
| 新 | **プロジェクトマネージャー** | 「WBS管理・品質・コスト・スケジュール管理・プロジェクト推進という**責任**を持つ業務が中心」 |

旧プロンプトの「進行管理・課題管理・調整・資料作成が主 → PMO やプロジェクトマネージャー」
という一行が、affinity 0.2（最遠）の2つを同列に扱わせていた。

**影響は 24pt。** 要求役割が PMO だと本物のPM人材が −9pt され、
PMO C級（議事録・PC手配・平均66万）が +15pt で上位に来る。順位が正反対になっていた。

判定は**動詞で決める**: 責任を持つ・決定する → PM ／ 指示する・レビューする → PL ／
支援する・伴走する・整理する → PMO。

### 残っている穴: 到達レベルが順位に効いていない

`role_affinity` はラベルしか見ないので、**PMO A級（RFP・ベンダ評価・平均97万）と
PMO C級（議事録・PC手配・平均66万）が、PM案件に対して同じ −9pt になる。**
上の求人は歓迎要件に「PL/PM/PMO経験（いずれか）」と書いており、A級のPMOは出して正解。

画面ではレベルのバッジが出るので営業は見分けられるが、順位には反映されていない。
直すには `role_affinity` に人材側のレベルを渡す必要があり、
`fetch_candidates_for_project` の改修を伴う（2026-08-31 に一度壊した関数なので慎重に）。

**現状、人材側の役割にAIは一切関与していない**（`scoreProseRoles` のregexのみ。AI校正のプロンプトは
techs/skillYears等が対象で roles を扱わない）。案件側の `requiredRole` だけAIが判定している。

したがって順序は:
1. regexに**必須裏付けと降格**を入れる（費用ゼロ・即日・実測で効果が測れる）
2. `role_affinity` を2軸式に置き換える
3. AI校正に**到達レベルA/B/C**の判定を足す
4. 画面に到達レベルと矛盾警告を出す
