# マッチング判断の再設計（2026-08-14）

## 背景：なぜ今のままでは使えないか

PMO歴10年の Y.T が「PowerShell→Azure Functions 移行（実装案件）」で 95点・1位になった
（2026-08-14 指摘）。スキル語（PowerShell・M365・EntraID・基本設計）は経歴書に実在するが、
PowerShell は単発のスクリプト作成のみで、主職種は社内SE・PMO。
一方、Haiku の提案所見はこれを正しく「条件付き・外部向け開発実績が限定的」と見抜いていた。

構造的な問題は3つ:

1. **ルールスコアが「適合度」を名乗っている**。実際に測れているのは条件の一致
   （単語・県・単価・年数）だけ。職種・スキルの深さ・直近性は見えない
2. **AIが2つに分裂し、賢い方（Haiku所見）が順位に効かず、浅い方（llama採点）が点数を出している**
3. **測る仕組みがない**。営業の採否ラベルが無く、変更が改善かどうか判定できない

## 基本原則

**ルールベース＝リコール（足切りと候補出し）。AI＝プレシジョン（最終判断）。
画面の主役はAIの判断（verdict）で、ルール値は「条件一致の内訳」として根拠付きで添える。**

守るべき既存の教訓:
- 判定の実装は1か所（`skill_satisfies` の前例）。新しい次元も「抽出時に1回計算して保存し、
  SQL・match-batch・フロントは読むだけ」にする。3か所実装の再発を防ぐ
- Edge Function は AI なしのまま（費用ゼロ制約）。深い読みは全部 ThinkCentre ワーカー
  （Haiku・サブスク枠）
- AI出力には必ず根拠（原文引用）を付けて画面に出す。根拠のない断定はしない

## ルールベースのあるべき姿

「点数」をやめて2段にする。

### ハードゲート（落とす理由が説明できるものだけ）
- 勤務地が通えない／単価が予算超過／派遣許可なし／必須スキル充足ゼロ
- 汎用スキルだけの合致は候補にしない（実装済み: `selective_skills`）

### 候補出しの順序付け（上位30〜50人を選ぶための内部値。画面の主役にしない）
今の配点を土台に2つ直す:

1. **スキルは有無でなく深さで加点**。`candidate_skills` / `raw_profile.skillYears` を使い、
   年数（capped）×直近性で重み付け。「PowerShell 3.5年・直近」と「記載1回・年数不明」を
   区別する。skillYears は既に取れているのにスコアが使っていないのが最大の無駄
2. **職種適合の次元を追加**。候補者の `roleProfile`（後述）と案件の `requiredRole`（後述）を
   照合。不一致は大減点。**ゲートにはしない**（2名補完案件では PMO が活きることもある）

## Claude AI解析パートのあるべき姿

3つの仕事に整理する。全部ワーカー（Haiku）に載る規模。

### 1. 人材の enrichment（取り込み後1回）
既存の補正に加えて `roleProfile` を抽出:
- 主たる職種の変遷（実装者/設計/PMO/インフラ/ヘルプデスク/テスト…）
- 各スキルの文脈（実装した/運用した/導入した/管理した）と最終使用時期
- 根拠は経歴の記述を引用して `raw_profile` に保存

### 2. 案件の interpretation（登録後1回・実装済みの拡張）
specialist・multiPerson・summary（実装済み）に **requiredRole** を追加:
この案件が求める役割（実装/設計/PMO/保守/ヘルプデスク）。案件側に無いと照合できない。

### 3. ペアの judgment（再マッチング後・上位N人）＝ 最終判断の本体
- 提案所見（required/verdict/pitch/strengths+根拠/gaps）を「おまけ」から本体に昇格
- ワーカーのキューに載せ、open 案件×上位10人に自動生成（8案件×10=80ペア、
  ワーカー実績75件/日で1日で回る。以後は差分のみ）
- **llama 採点（Cerebras/Groq/Gemini の3段）はこれに置き換えて廃止**
- 再マッチングで顔ぶれが変わったら該当ペアの所見を無効化して再生成

### 表示順位
`verdict 段階（推せる > 条件付き > 見送り > 未生成）→ ルール内部値` の辞書順。
95点の条件付きより 80点の推せるが上に来るのが正しい。

## 学習ループ（「最強」の条件）

- 「この人に決定」「不採用」を**ラベルとして保存**し、判断の golden set を作る
  （Excel golden と同じ思想）
- 配点・プロンプトを変えるたびに precision@5（営業が採った人を上位に出せたか）を測る。
  物差しが無い改善は全部感覚になる

## 実装順

| # | 内容 | 効果 | 備考 |
|---|---|---|---|
| 1 | judgment の本体化（所見をワーカーキュー化・verdict で並び替え・llama 採点廃止） | Y.T 問題が順位上も解消 | コードは既にある。キュー化と並び替えのみ |
| 2 | skillYears をルール順序付けに反映 | 深さ・直近性が順位に効く | データは既にある。SQL 修正のみ。`gen_fetch_candidates` 方式で機械生成 |
| 3 | roleProfile / requiredRole 抽出＋職種適合の次元 | 構造的に再発防止 | プロンプト拡張＋スキーマ。判定は保存値を読むだけの形にする |
| 4 | 採否ラベル保存＋precision 計測 | 以後の全変更の物差し | submissions.status は既にある。集計スクリプトから |

1と2だけでも Y.T 型の問題は画面・順位ともに解消する。

## 注意（実装時）

- `fetch_candidates_for_project` を触るときは手で書き写さず
  `python scripts/gen_fetch_candidates_nice.py` 方式で機械生成（写経ミスで配点が変わる）
- スキル判定を変えたら `scripts/sql/test_skill_matching.sql` /
  `test_skill_matching_rpc_parity.sql` を必ず回す
- 変更前後で `scripts/snapshot_rpc_ranking.mjs` → `compare_rpc_ranking.mjs`（1案件・少件数で足りる。
  egress 注意）
- anon の statement_timeout は 15秒。RPC が重くなったら
  `probe_fetch_candidates_timing.mjs`（anon）で本番条件を測る
